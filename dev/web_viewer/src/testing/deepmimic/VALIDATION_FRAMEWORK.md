# DeepMimic ONNX Validation Framework

## Overview

This validation framework ensures that the JavaScript ONNX Runtime Web implementation produces identical outputs to the Python TensorFlow implementation across different execution providers (WebGPU, WebNN, WebGL, WASM).

## Key Components

### 1. Python Validation System (`validate_models.py`)
- **Purpose**: Generate reference data and validate TensorFlow → ONNX conversion
- **Features**:
  - Loads original TensorFlow checkpoints
  - Converts to ONNX and validates conversion accuracy
  - Creates comprehensive test cases (zero state, random, walking poses, etc.)
  - Generates JavaScript test data with expected outputs
  - Provides detailed comparison metrics with configurable tolerances

### 2. JavaScript Validation Framework (`onnx_validation_framework.js`)
- **Purpose**: Validate JavaScript ONNX inference against Python reference data
- **Features**:
  - Tests all available execution providers automatically
  - Loads reference data generated by Python validation
  - Runs identical test cases and compares outputs
  - Provides detailed performance benchmarking
  - Supports configurable tolerance levels

### 3. Interactive Validation Demo (`validation_demo.html`)
- **Purpose**: Visual interface for comprehensive testing and validation
- **Features**:
  - Real-time execution provider availability detection
  - Model and reference data loading interface
  - Live validation results with detailed metrics
  - Performance comparison across execution providers
  - Export functionality for validation reports

## Test Cases

The framework uses standardized test cases to ensure comprehensive validation:

### 1. **Zero State**
- All-zeros input vector
- Tests model behavior at origin
- Validates basic inference pipeline

### 2. **Default Pose**
- Standard humanoid standing pose
- Y position = 1.0 (height)
- Quaternion = [0,0,0,1] (identity rotation)

### 3. **Random Normal**
- Random values from normal distribution (μ=0, σ=0.1)
- Seed = 42 for reproducibility
- Tests model robustness

### 4. **Walking State**
- Forward velocity = 1.0
- Small joint oscillations
- Simulates typical walking motion

### 5. **Extreme Values**
- Large position and velocity values
- Tests numerical stability
- Edge case validation

## Validation Metrics

### Tolerance Levels
- **Absolute Tolerance**: 1e-5 (default)
- **Relative Tolerance**: 1e-4 (default)
- **Configurable**: Can be adjusted based on model requirements

### Comparison Metrics
- **Maximum Absolute Difference**: `max(|tf_output - js_output|)`
- **Maximum Relative Difference**: `max(|tf_output - js_output| / |tf_output|)`
- **Mean Absolute/Relative Differences**: Average across all outputs
- **Pass/Fail Status**: Based on tolerance thresholds

## Execution Provider Testing

### WebGPU
- **Best Performance**: Hardware-accelerated GPU compute
- **Requirements**: Chrome 94+ with WebGPU enabled
- **Expected**: 5-15ms inference times

### WebNN
- **Good Performance**: Hardware-accelerated neural network APIs
- **Requirements**: Browsers with WebNN support
- **Expected**: 10-25ms inference times

### WebGL
- **Good Compatibility**: GPU acceleration via WebGL
- **Requirements**: Modern browsers with WebGL support
- **Expected**: 15-30ms inference times

### WASM
- **Universal Fallback**: CPU-based execution
- **Requirements**: Any modern browser
- **Expected**: 50-150ms inference times

## Performance Benchmarking

### Metrics Collected
- **Inference Time**: Per-frame inference latency
- **Memory Usage**: Model loading and runtime memory
- **Throughput**: Frames per second capability
- **Stability**: Consistency across multiple runs

### Benchmark Process
1. Load model with specific execution provider
2. Run 100 inference iterations with dummy input
3. Calculate statistics: mean, min, max, standard deviation
4. Compare across execution providers

## Error Handling

### Common Issues and Solutions

#### 1. Model Loading Failures
- **Cause**: Corrupted ONNX files or unsupported operations
- **Solution**: Re-run conversion, check TensorFlow model integrity
- **Debug**: Check browser console for specific ONNX Runtime errors

#### 2. Tolerance Failures
- **Cause**: Numerical precision differences between TensorFlow and ONNX
- **Solution**: Adjust tolerance levels, investigate specific operations
- **Debug**: Examine detailed comparison metrics

#### 3. Execution Provider Failures
- **Cause**: Hardware incompatibility or driver issues
- **Solution**: Fallback to more compatible providers
- **Debug**: Test each provider individually

#### 4. Shape Mismatches
- **Cause**: Incorrect model conversion or input preparation
- **Solution**: Verify model architecture and input dimensions
- **Debug**: Check input/output shapes in validation results

## Troubleshooting Guide

### Python Validation Issues

#### TensorFlow Loading Errors
```bash
# Check TensorFlow installation
python -c "import tensorflow as tf; print(tf.__version__)"

# Reinstall if needed
pip install --upgrade tensorflow
```

#### ONNX Conversion Failures
```bash
# Check tf2onnx installation
python -c "import tf2onnx; print(tf2onnx.__version__)"

# Enable verbose logging
python convert_to_onnx.py --verbose
```

### JavaScript Validation Issues

#### ONNX Runtime Loading
- Ensure ONNX Runtime Web script is loaded before validation framework
- Check network connectivity for CDN resources
- Use local copy if needed

#### Execution Provider Failures
```javascript
// Check available providers
console.log('ONNX providers:', ort.env.executionProviders);

// Test provider manually
const session = await ort.InferenceSession.create(modelPath, {
    executionProviders: ['webgl']
});
```

#### CORS Issues
- Must serve files via HTTP server, not file:// protocol
- Use `python3 -m http.server 8080` for local testing
- Configure CORS headers if needed for production

## Best Practices

### Model Validation
1. **Always validate conversion**: Run Python validation before JavaScript testing
2. **Use multiple test cases**: Don't rely on single input validation
3. **Check edge cases**: Test with extreme values and boundary conditions
4. **Monitor performance**: Track inference times across updates

### JavaScript Testing
1. **Test all providers**: Ensure compatibility across execution backends
2. **Use appropriate tolerances**: Balance precision with practical requirements
3. **Benchmark regularly**: Performance can vary with browser/driver updates
4. **Validate integration**: Test full pipeline, not just inference

### Debugging Workflow
1. **Start with Python**: Ensure TensorFlow → ONNX conversion is correct
2. **Test single provider**: Isolate JavaScript issues to specific backends
3. **Compare outputs**: Use detailed metrics to identify specific differences
4. **Check intermediate values**: Add logging to trace computation steps
